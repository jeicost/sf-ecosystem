## Architecture Overview

The SF ecosystem uses **two Supabase projects**:

### Project 1: nnevhtfxuawexliwlbmh (Shared — Primary)
- **Used by:** MIRA, AI Agency SF, SF-CRM, SF-Sales-Engine
- **Cost:** $25/mo (Pro plan)
- **Storage:** Postgres + pgvector + realtime subscriptions + storage buckets
- **Why shared?** Cross-app RAG queries (e.g., MIRA can query ai-agency audits for training data)

### Project 2: dmzecrlkclocqaywkjtc (CMS only)
- **Used by:** SF-CMS
- **Cost:** $25/mo (Pro plan) — separate for data isolation
- **Storage:** Postgres only (no pgvector, limited realtime)
- **Why separate?** CMS content is generated by SF team, not clients. Isolating it prevents accidental data leaks between published websites.

## Adding a New App: Supabase Setup

### Step 1: Decide on Database
- **Multi-client/workspace app?** Use shared project (nnevhtfxuawexliwlbmh)
- **Sensitive/isolated data?** Use separate project

### Step 2: Get Credentials
**From Supabase Dashboard:**
1. Go to Project Settings → API
2. Copy:
   - Project URL → `NEXT_PUBLIC_SUPABASE_URL`
   - `anon` key → `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `service_role` key → `SUPABASE_SERVICE_ROLE_KEY`

### Step 3: Create .env.local
```bash
NEXT_PUBLIC_SUPABASE_URL=https://xxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=ey...
SUPABASE_SERVICE_ROLE_KEY=ey...
```

### Step 4: Create Supabase Client
**Pattern A (Browser):**
```typescript
// lib/supabase.ts
import { createBrowserClient } from '@supabase/ssr'

export function createClient() {
  return createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!
  )
}
```

**Pattern B (Server):**
```typescript
// lib/supabase.ts
import { createClient as _createClient } from '@supabase/supabase-js'

export function adminClient() {
  return _createClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.SUPABASE_SERVICE_ROLE_KEY!
  )
}
```

### Step 5: Deploy to Vercel
Set environment variables in Vercel Project Settings:
```
NEXT_PUBLIC_SUPABASE_URL=https://xxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=ey...
SUPABASE_SERVICE_ROLE_KEY=ey...
```

## Shared Database: Cross-App Queries

The shared database (nnevhtfxuawexliwlbmh) allows apps to reference each other's data.

### Example: MIRA querying AI Agency audits for training

**Setup:**
- AI Agency stores audits in `ai_agency_audits` table with `client_id`
- MIRA portal can query `ai_agency_audits` for clients that have both services

**Query:**
```typescript
// In MIRA (mira/portal)
const { data: audits } = await supabase
  .from('ai_agency_audits')  // Different app's table
  .select('*')
  .eq('client_id', activeClient.id)
  // RLS prevents access outside client_id
```

**RLS ensures isolation:**
- MIRA client A cannot see AI Agency audits from client B
- Service role (server code) must explicitly filter

## CMS Database: Why Separate?

SF-CMS uses a separate database (dmzecrlkclocqaywkjtc) because:

1. **Content Isolation:** CMS content is generated by SF team, published to client websites. Separating it prevents:
   - Accidental data leaks between websites (e.g., copying Discoolver content to Salsa Burgers)
   - Scope creep of shared database (CMS is more of a content store, not an operational database)

2. **Cost Control:** CMS has simpler requirements (no pgvector, no realtime). Separate project lets it use a cheaper tier if needed.

3. **Access Control:** CMS has different auth model (admin-only) vs. MIRA (multi-client). Separate database makes this clear.

## RLS Bypass: Service Role vs. Anon Key

| Operation | Anon Key | Service Key |
|-----------|----------|-------------|
| SELECT own client data | ✅ Allowed (RLS filters) | ✅ Allowed (no RLS) |
| SELECT other client data | ❌ Blocked by RLS | ✅ Allowed (bypasses RLS) |
| INSERT with client_id | ✅ Allowed (if has policy) | ✅ Allowed |

**Best Practice:**
- Browser code: always use anon key + RLS protection
- Server code: use service key, but still filter by client_id/workspace_id manually

```typescript
// Server code: Always filter, don't rely only on RLS
const { data } = await adminClient
  .from('brand_profiles')
  .select('*')
  .eq('client_id', clientId)  // ← Manual filter (defense in depth)
  // RLS may not apply if service role is used
```

## Monitoring & Maintenance

### Check Active Connections
```sql
-- In Supabase SQL Editor
SELECT 
  datname as database,
  usename as user,
  COUNT(*) as connections
FROM pg_stat_activity
GROUP BY datname, usename
ORDER BY connections DESC;
```

### Monitor Realtime Subscriptions (MIRA)
```typescript
// Check active subscriptions
const channels = supabase.getChannels()
console.log(`Active subscriptions: ${channels.length}`)
```

### Backup Strategy
- **Automated:** Supabase Pro includes daily backups
- **Manual:** Use Supabase dashboard → Database → Backups
- **Scheduled:** Set up pg_dump to S3 for long-term archival

## Troubleshooting

### Issue: "Invalid token" error on login
**Cause:** Wrong `NEXT_PUBLIC_SUPABASE_URL` or `NEXT_PUBLIC_SUPABASE_ANON_KEY`
**Fix:**
1. Verify URLs match between `.env.local` and Vercel Project Settings
2. Check keys haven't expired (very rare, but possible)
3. Redeploy app with correct vars

### Issue: Queries return empty array (RLS blocking)
**Cause:** `user_metadata.client_id` not set or wrong
**Fix:**
1. Check: `SELECT auth.uid(), user_metadata FROM auth.users WHERE id = auth.uid()`
2. If `user_metadata.client_id` is null, set it via signup handler or admin update
3. Verify RLS policy syntax is correct

### Issue: Cross-app query not working
**Cause:** RLS policy filters out data
**Fix:**
- Querying app's user must have access to data via RLS
- If querying another app's table, RLS must permit it
- Use service role + manual filtering as fallback
