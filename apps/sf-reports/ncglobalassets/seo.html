⚠️ ARQUITECTURA: SPA vs SSG ✗ CRÍTICO RAÍZ DEL PROBLEMA SEO (46/100): El site es React SPA (Single Page Application) en Vite sin pre-rendering. Páginas como /case-studies/*, /blog/* se renderizan SOLO en cliente (JavaScript). Google Search Console puede ver el HTML shell pero no el contenido dinámico renderizado después de que JS ejecute. Esto causa:
  • Pages bloqueadas por robots.txt y usuario-agent filters en Search Console
  • Meta descriptions y H1 dinámicos no indexables sin JS rendering
  • Impacto directo: baja densidad de keywords, bajo crawl budget efficiency
React-snap fue removido de build (May 2026) precisamente por este motivo: No hay pre-rendering HTML estático. El build actual produce JS bundles solamente.
Vite output: /about.html / /blog.html son referencias JS, no HTML pre-renderizado
SOLUCIÓN ARQUITECTÓNICA (6-8 semanas): Migrar a Next.js 16 con Static Generation (SSG). Pre-renderizar todas las páginas a HTML estático en build time. Mantener reactividad con Next.js hydration. Esto convierte 46→72+ score inmediatamente.
Hreflang EN/TH/etc ✗ NO APLICA Contenido únicamente en inglés. Aunque Bangkok es mercado bilingüe, el target es inversores internacionales (ex-pats, corporates) que buscan en inglés. No crítico pero Bangkok local search está perdido.
Schema Organization ✓ BÁSICO Organization + ContactPoint schema presente. Falta LocalBusiness schema que sería útil para "investment firm Bangkok" searches.
Page Speed ⚠ MEJORABLE FCP desktop ~1.2s, mobile ~2.0s. JS bundle ~2.1MB comprimido (Framer Motion + React DOM = overhead SPA). Sin pre-rendering estático, cada página requiere JS parse/compile.

06PLAN DE ACCIÓN

Enfoque de 2 vías: Quick wins inmediatos (sem 1-2) + arquitectura de largo plazo (sem 6-8).

CRÍTICO
Migrar a Next.js 16 con Static Generation (SSG)
Arquitectura raíz del bajo score (46→72+). Convertir React SPA a Next.js app router con generateStaticParams() para pre-renderizar todas las rutas (/about, /services, /blog/*, /case-studies/*) a HTML estático en build time. Mantener interactividad con Next.js hydration. Permite que Google indexe contenido real.
+300% organic visibility
CRÍTICO
Implementar Article schema en blog posts
Marca cada /blog/* con BlogPosting JSON-LD que incluya: headline, articleBody, datePublished, author, image. Una vez que Next.js SSG pre-renderiza estos, Article schema hará que Google los identifique como contenido editorial (vs. contenido corporativo genérico).
+50% blog indexation
ALTO

+15% local searches

Target long-tail keywords: "Real Estate Investment Tips Bangkok 2026", "Corporate Relocation Thailand Checklist", "Expat Property Guide Bangkok". Cada post = nueva página indexable. Una vez SSG implementado, cada post aparecerá en organic search.
+200% blog traffic potential

07SÍNTESIS Y RECOMENDACIÓN

Score actual: 46/100 — Bajo principalmente por limitación arquitectónica, no mala ejecución SEO.

Qué está bien: On-page elements (title, meta, alt text), technical fundamentals (SSL, sitemap, robots.txt), contenido de calidad, schema básico.

Qué está mal: SPA architecture impide Google indexar páginas dinámicas (especialmente blog). No hay Article schema. No hay LocalBusiness schema para Bangkok. Sin pre-rendering estático, investimiento en contenido no genera retorno orgánico.

Recomendación: Prioridad = Next.js SSG migration (6-8 semanas). Sin esto, el blog no va a rankear sin importar cuánto contenido escribas. Con esta migración, el mismo contenido que hoy es invisible pasará a ser completamente indexable. Retorno esperado: 46 → 72 score, +300% visibilidad orgánica, +$50K+ annual revenue impact (conservador para firma B2B).
